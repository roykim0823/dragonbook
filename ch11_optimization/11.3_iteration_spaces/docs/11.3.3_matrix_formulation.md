# §11.3.3 Matrix Formulation of Inequalities

Part of [11.3 Iteration Spaces](../README.md) · previous: [§11.3.2](11.3.2_execution_order.md) · next: [§11.3.4](11.3.4_symbolic_constants.md)

**Matrix form `Bx + b ≥ 0`** (Eq. (11.1); the book works this example as Example 11.8, Fig. 11.13). Write every inequality in the standard shape **`(coefficients)·x + constant ≥ 0`**. There are only two rewriting moves, and only one rule to remember:

* move everything to the left side;
* if you multiply by a negative number, **flip** the inequality.

Doing that to the four inequalities of Fig. 11.10:

```
 i ≥ 0        →   i          ≥ 0   →  ( 1)i + ( 0)j + 0 ≥ 0
 i ≤ 5        →  −i + 5      ≥ 0   →  (−1)i + ( 0)j + 5 ≥ 0      (multiplied by −1: ≤ became ≥)
 j ≥ i        →  −i + j      ≥ 0   →  (−1)i + ( 1)j + 0 ≥ 0
 j ≤ 7        →  −j + 7      ≥ 0   →  ( 0)i + (−1)j + 7 ≥ 0
```

Each line now has the shape `u·i + v·j + w ≥ 0`. Stack the coefficient pairs `[u, v]` as the rows of a matrix `B` and the constants `w` as the entries of a vector `b`, and the four inequalities become one matrix-vector inequality. That is the book's Fig. 11.13 (Example 11.8):

**Figure 11.13: Matrix-vector multiplication and a vector inequality represents the inequalities defining an iteration space**
```
    ┌  1   0 ┐           ┌ 0 ┐     ┌ 0 ┐
    │ −1   0 │   ┌ i ┐   │ 5 │     │ 0 │
    │ −1   1 │ · └ j ┘ + │ 0 │  ≥  │ 0 │
    └  0  −1 ┘           └ 7 ┘     └ 0 ┘
        B         x        b
```

Row 1 of the product is `i ≥ 0`, row 2 is `−i + 5 ≥ 0`, row 3 is `−i + j ≥ 0`, row 4 is `−j + 7 ≥ 0`: the same four lines as above, read back. In this notation the iteration space is `{ (i, j) ∈ Z² | B·(i, j) + b ≥ 0 }`, which is Eq. (11.1).

Two facts you will use constantly. Both come from reading a row as an inequality *about one variable* and solving for it.

**Fact 1: the sign of a variable's coefficient tells you which kind of bound the row is.** Take any row and pick a variable `v`. Move every other term to the right-hand side; call that right-hand side the *rest*. If the coefficient of `v` is positive, the row says `v ≥ something`, a **lower bound**. If it is negative, dividing by it flips the inequality, so the row says `v ≤ something`, an **upper bound**. If it is zero, the row says nothing about `v`.

Doing this for each of the four rows of Fig. 11.10, first for `i`, then for `j`:

```
 row                 solve for i                       solve for j
 ──────────────────  ────────────────────────────────  ────────────────────────────────
 ( 1)i + ( 0)j + 0   i ≥ 0            coef +1 → LOWER  coef 0 → says nothing about j
 (−1)i + ( 0)j + 5   −i ≥ −5 → i ≤ 5  coef −1 → UPPER  coef 0 → says nothing about j
 (−1)i + ( 1)j + 0   −i ≥ −j → i ≤ j  coef −1 → UPPER  j ≥ i            coef +1 → LOWER
 ( 0)i + (−1)j + 7   coef 0 → says nothing about i     −j ≥ −7 → j ≤ 7  coef −1 → UPPER
```

So the same row `−i + j ≥ 0` is an *upper* bound when you are asking about `i` (`i ≤ j`) and a *lower* bound when you are asking about `j` (`j ≥ i`). Which one it is depends on which variable you are solving for, not on the row. This is exactly why the inner loop in *Why the inner loop is easy* (§11.3.5) gets `i ≤ min(5, j)`: the two rows with a negative `i` coefficient are the two upper bounds on `i`.

**Fact 2: the bound is `rest / |coefficient|`, rounded towards the inside.** With a coefficient of ±1 nothing needs dividing. With a larger coefficient the division can produce a fraction, and since `v` is an integer the fraction must be rounded *inwards*: a lower bound rounds **up** (`⌈·⌉`), an upper bound rounds **down** (`⌊·⌋`). Two made-up rows show the pattern:

```
 2i − j + 3 ≥ 0    →   2i ≥ j − 3    →   i ≥ (j − 3)/2    →   i ≥ ⌈(j − 3)/2⌉     (lower bound, coef +2)
−3i + j + 1 ≥ 0    →   3i ≤ j + 1    →   i ≤ (j + 1)/3    →   i ≤ ⌊(j + 1)/3⌋     (upper bound, coef −3)
```

Check the second one with `j = 5`: `i ≤ 6/3 = 2`, so `i = 2` is allowed; with `j = 4`: `i ≤ 5/3 ≈ 1.67`, so the largest integer `i` is 1, which is `⌊5/3⌋`. The generated loops in the exercise solutions (§11.3.7) contain `ceil_div(...)` and `floor_div(...)` for precisely this reason (e.g. Exercise 11.3.7(a) has `j <= floor_div(d + 39, 2)`).

In `code/include/poly.h` (the data model shared by every numbered program in `code/src/`) a row is a `Constraint`: a coefficient array `a`, one entry per column of `B`, and a constant `c`, meaning `a[0]·x₀ + a[1]·x₁ + … + c ≥ 0`. A `Polyhedron` is the list of variable names (one per column) plus its rows. The first thing the Fourier–Motzkin function `eliminate(S, m)` in `code/include/fourier_motzkin.h` does, when asked to eliminate column `m` from polyhedron `S`, is walk every row of `S` and apply Fact 1 to sort it into one of three piles: lower bounds on `x_m`, upper bounds on `x_m`, or rows that do not mention `x_m` (these are copied unchanged into the result). That sort is the first thing quoted under `fourier_motzkin.h` in [the code bundle](code_bundle.md#fourier_motzkinh).

The two piles `lower` and `upper` are then paired up as described in *Algorithm 11.11: the recipe* in [§11.3.5](11.3.5_controlling_execution_order.md). Fact 2 is applied later, when the bounds are printed as loop limits: the emitter uses `ceil_div`/`floor_div` for any coefficient other than ±1 (Algorithm 11.13 and *Integers vs. rationals*, both in [§11.3.5](11.3.5_controlling_execution_order.md)).

## Code example 02 — `./run.sh 2`

Program 02 builds this polyhedron row by row with `ge0` (each call is one inequality, written as `coefficients, constant`), prints the rows, and counts the integer points two ways: by running the loop nest of Fig. 11.10 and by brute-force enumeration of the polyhedron. Both must give 33, which is the first check that the loop and the inequalities describe the same set. The brute force, `enumerateBox(poly, lo, hi)`, tries every integer point of the square `[lo, hi]²` and keeps those that satisfy all four rows, so `lo` and `hi` only have to enclose the polyhedron; `−2` and `12` are nothing more than a generous guess around `0..5 × 0..7`. Because a box that is too small would silently undercount, the program also enumerates a much larger box and checks that it finds nothing new. Every later program that calls `enumerateBox` uses a box chosen the same way.

The two types the program is built from, `Constraint` and `Polyhedron` with its `ge0` and `column`, are quoted and explained in [the code bundle](code_bundle.md#polyh).

Where each line of the output comes from (the printing functions are quoted in [the code bundle](code_bundle.md#polyh)):

| line(s) of `./run.sh 2` | printed by |
|---|---|
| `Example 11.8: B i + b >= 0 for Fig. 11.10  (vars: i j )` | `printRows`: the title, then the variable names |
| the four indented `… >= 0` rows | `printRows` → `rowStr` → `exprStr` (and `signStr` for each sign) |
| `Fig. 11.10 original nest: 33 iterations` and the two lines after it | the program's own `std::cout` statements |

**code/src/02_example_11_8_matrix_form.cpp**
```cpp
#include "verify.h"

int main() {
  Polyhedron poly; // Fig. 11.10:  for (i=0;i<=5;i++) for (j=i;j<=7;j++)
  poly.vars = {"i", "j"};
  poly.ge0({{"i", 1}}, 0)            //  i     >= 0     i >= 0 => poly.rows[0] = [1, 0]  c=0
      .ge0({{"i", -1}}, 5)           // -i + 5 >= 0     i <= 5 => poly.rows[1] = [-1, 0] c=5
      .ge0({{"i", -1}, {"j", 1}}, 0) // -i + j >= 0     j >= i => poly.rows[2] = [-1, 1] c=0
      .ge0({{"j", -1}}, 7);          // -j + 7 >= 0     j <= 7 => poly.rows[3] = [0, -1] c=7
  printRows(poly, "Example 11.8: B i + b >= 0 for Fig. 11.10");

  long byLoop = 0; // count the iterations by running the nest
  for (long i = 0; i <= 5; i++)
    for (long j = i; j <= 7; j++)
      byLoop++;

  // enumerateBox tries every integer point of the square [lo, hi]^2 and keeps
  // those that satisfy all four rows, so the box only has to CONTAIN the
  // polyhedron: 0 <= i <= 5 and 0 <= j <= 7 fit inside [-2, 12]^2 with room to
  // spare. A box that is too small would silently undercount, so also check
  // that a much bigger box finds nothing new.
  size_t byPoly = enumerateBox(poly, -2, 12).size();
  size_t byBiggerBox = enumerateBox(poly, -20, 30).size();
  std::cout << "Fig. 11.10 original nest: " << byLoop << " iterations\n";
  std::cout << "integer points of the polyhedron (brute force): " << byPoly
            << "  " << ((long)byPoly == byLoop ? "== loop nest" : "MISMATCH")
            << "\n";
  std::cout << "box check: [-2,12]^2 gives " << byPoly << ", [-20,30]^2 gives "
            << byBiggerBox << "  "
            << (byBiggerBox == byPoly ? "(same: the box is big enough)"
                                      : "MISMATCH")
            << "\n";
}
```

`enumerateBox` and the three helpers under it are quoted and explained in [the code bundle](code_bundle.md#verifyh); it is the ground truth that every later verification rests on.
